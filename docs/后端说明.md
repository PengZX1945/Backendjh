# 后端说明

对应《精弘大作业（失物招领系统）接口文档》全部六个分组：用户、物品、认领申请、发布审核、公告、系统管理。
接口清单见 [`../api/README.md`](../api/README.md)，运行方式见 [`../README.md`](../README.md)。

## 1. 目录结构与职责

```
cmd/server/            服务入口：读配置 → 连库迁移 → 起 HTTP → 优雅退出
internal/
├── config/            配置加载、默认值与环境变量覆盖
├── database/          连接与建表；SQLite 与 MySQL 的差异隔离在此
├── model/             实体、状态常量、领域判断（IsVisibleTo / CanBeManagedBy / IsBackOffice）
├── dto/               请求体、响应体、查询条件
├── repository/        数据访问层，唯一 import gorm 的地方
├── service/           业务规则：状态机、权限判定、错误码选择
├── handler/           HTTP 适配层：解析请求 → 调 service → 写响应
├── middleware/        统一响应 / 鉴权 / 角色 / CORS / 访问日志
├── router/            组合根与路由表
└── token/             JWT 签发与校验
pkg/
├── apperr/            业务异常类型
├── errcode/           错误码表（code ↔ msg ↔ HTTP 状态码）
├── response/          统一响应信封
├── logger/            日志出口
└── timeutil/          时间串格式
```

依赖方向是单向的：`router → handler → service → repository → model`，
`pkg/*` 不依赖任何 internal 包。

三条纪律把分层落到实处：

- **handler 不做业务判断**。它只解析请求、调 service、写响应。因此每个 handler 都能一眼看完，
  业务规则也不会沿着接口数量被复制多份。
- **service 不 import gin，也不 import gorm**。业务规则因此可以脱离 HTTP 与 ORM 单独推敲；
  「查不到记录」这种 ORM 语义在仓储层翻译成 `repository.ErrNotFound`，再在 service 层
  翻译成业务错误码 4，不让 ORM 细节沿着调用链上渗。
- **repository 不返回裸 `*gorm.DB`**。查询条件必须走具名的 filter 结构体，
  「能按什么条件查」因此是显式的，SQL 拼装权也不会散到上层。

## 2. 统一错误码与统一响应

### 2.1 错误码只有一个真相源

`pkg/errcode` 集中定义 `code ↔ msg ↔ HTTP 状态码` 三者的映射。业务代码只引用常量，
不出现任何字面量 —— 改一次文案或状态码只需动一处，也就不会出现「同一个 code 在不同接口
返回不同 msg」这类不一致。未登记的 code 一律回落为 114。

### 2.2 失败响应怎么收口

`middleware.ErrorHandler` 就是作业要求的「业务异常统一响应中间件」。约定是：

- handler 与 service **不自己写错误响应**，只把 error 交给 gin 的错误收集器（`c.Error(err)`）；
- 中间件在整条处理链跑完后统一收口：`*apperr.Error`（可预期的业务失败）按其错误码输出
  `{code, msg, data: null}`；其他 error（未预期异常）记一条带原始原因的日志，对外只回 114。

这样做的实际收益：对外永远不泄露数据库或内部细节，日志里却留下了完整原因；
同时「有没有哪个接口忘了处理错误」不再是一个需要靠人眼排查的问题 —— 漏了的 error
会被中间件兜成 114 并打日志，而不是静默返回 200。

`response.OK` / `response.Fail` 是全站唯一的响应出口，信封结构、字段命名与
`data` 为 null 的语义因此有唯一保证（`data` 不带 `omitempty`：空值必须显式为 `null`
而不是被省略，前端要靠 `data` 键的存在与否区分信封与裸对象）。

### 2.3 为什么把业务错误码映射到 4xx/5xx

文档为多数接口标注了 4xx/5xx，前端的错误处理也依赖 HTTP 状态码做分流：
`401` 与业务码 2 触发「会话失效」跳登录页，`404` 或业务码 4 让详情页渲染空态而不是错误态。
因此后端按错误码表输出对应状态码，而不是一律返回 `200 + 业务码` —— 后者会让前端
丢失这条分流依据。

## 3. 鉴权

### 3.1 选型与载荷

JWT（HS256）。作业要求「后端使用常见的鉴权方式」，前端又要求「登录状态持久化」，
而 JWT 无状态、自包含，前端存进 localStorage 后按 `Authorization: Bearer` 携带即可，
服务端无需维护会话存储。

载荷里**只放 `user_id` 与 `username`，不放 `role`**。角色每次请求都从数据库读，
这样管理员刚把某人提为管理员，其下一个请求立刻生效，不必等旧凭证过期 ——
否则会出现「已撤销管理员权限的人，在凭证过期前仍然进得了后台」这种说不清的窗口。

`RequireRole` 因此也**自带凭证校验**，使用时不必再串一道 `Authenticate`。
这是刻意的：若角色判断只依赖上下文里已有的用户，一旦漏配鉴权中间件，所有后台接口
都会因为「用户为空」而统一返回未登录 —— 一个既不像权限错误、又很难从返回码上看出来的
失效方式。把「验凭证」与「查角色」合成一个中间件，误用的可能性就没有了。

### 3.2 比文档多做的一点

文档把错误码 10（账号已被禁用）限定在登录环节。后端把这条规则扩展到凭证校验：
被禁用的账号即使持有有效凭证也会被拦下。否则封禁一个账号要等它的凭证过期才生效。

### 3.3 越权判定不只靠接口设计

需要「本人才能操作」的接口（改资料、改认领申请、删物品等），都在 service 层显式判定
归属，而不是依赖「前端不会传别人的 ID」。文档里 `PUT /auth/profile` 的 `user_id` 是
query 参数（「从 auth 传入」），后端以鉴权中间件注入的身份为准，另传一个不属于自己的
`user_id` 判越权（3）。

## 4. 路由层的两处取舍

### 4.1 `{type}` 与 `{option}` 用静态路径表达

文档把发布接口写作 `POST /items/{type}`、审核写作 `POST /admin/items/{item_id}/{option}`。
但 gin 的路由树要求**同一位置上出现的通配符必须同名**：
`POST /items/{type}` 与 `POST /items/{item_id}/close` 会在同一层出现 `:type` 与 `:item_id`
两个不同名的通配符，注册时直接 panic。

因此凡是取值封闭的路径段都拆成静态路径：发布拆成 `POST /items/lost` 与 `POST /items/found`，
审核拆成 `.../approve` 与 `.../reject`。**对客户端而言 URL 与文档完全一致**，
顺带把「大类只能是这两个值」「option 只能是这两种」变成了路由层的硬约束 ——
非法取值根本不会命中路由，不必在函数体里再校验一次。

### 4.2 尾斜杠两种形态都登记

文档里多个路径带尾斜杠（`/items/list/{type}/`、`/my/claims/`…），前端也按原样请求，
而同一份文档里另一些路径又不带。若只登记其中一种，另一种会落到 gin 的 307 重定向：
对 POST/PUT/DELETE 而言多一次往返，且不同代理对 307 的处理并不一致。
路由层统一把两种形态都登记，请求无论怎么写都能直达处理器。

未命中的路径与错误的方法也走统一信封（`NoRoute` / `NoMethod` 回 code 4），
不会漏出框架自带的纯文本 `404 page not found`。

## 5. 关键约定

**时间的存法**

时间统一以 `VARCHAR(20)` 存 `YYYY-MM-DD HH:mm:ss`，取**本地时间**。三条理由：

1. 该格式的字典序与时间序一致，`happen_time` / `created_time` 可以直接用字符串比较排序；
2. 前端 `utils/date-format.ts` 把不带时区的日期串按**本地时间**解析
   （`new Date('2026-10-06T09:17:35')`），发帖时也用 `datetime-local` 的本地值回传，
   两者正好对上，往返无偏移；
3. 不随数据库变化 —— SQLite 与 MySQL 下行为完全一致。

（联调时的一处发现：前端联调用的 mock 生成的是 **UTC** 串，而前端按本地解析，
所以 mock 下相对时间其实有 8 小时偏差。后端按本地时间存反而修正了这一点。）

**物品修改是「全段更新」**

`PUT /items/{item_id}` 按文档要求全段覆盖，且改完状态重置为待审核、清空驳回理由。
「先发正常内容、过审后再改成违规内容」因此被堵住。未填的可选字段按提交值覆盖，
不做「缺省保留旧值」——前端提交时已把全部字段带齐。

**认领审批是原子操作**

通过一条认领申请会连带三处变更：本条置为已通过 → 对应物品置为已关闭 →
同一物品的其他待审批申请自动驳回。三步必须同生共死，否则会留下「物品已关闭但其他申请
还挂着待审批」的中间态，管理员稍后处理时会对着一个已关闭的物品继续审批。
因此这三步用一个事务封装在 `ClaimRepository.Approve` 里。

**图片字段的落库方式**

帖子图片是 `[]string`，用 GORM 的 `serializer:json` 落库。一个连带约束：全段更新必须用
结构体维度的写入（`Save`），不能把该字段塞进 `map[string]any` —— serializer 只在结构体
写入时生效，走 map 会把 `[]string` 原样交给驱动，SQLite 无法绑定该类型而报错。

**上传的两道校验**

扩展名白名单 + 内容嗅探（`http.DetectContentType`）。只看扩展名会让改了后缀的脚本文件
混进来，只看内容又会误伤头部不含 magic 的合法图片。落盘用随机文件名而不是原始文件名 ——
原始名可能重复、可能带路径分隔符，直接落盘会成为路径穿越的入口。
图片经 `/api/uploads/` 前缀对外提供，挂在 `/api` 之下使前端开发态代理与生产态反代
都能直接命中，无需额外配置转发规则。

## 6. 文档中的不确定点与本后端的处理

前端的交付说明列了 7 条「后端契约中的不确定点」，这里逐条给出后端定稿后的口径：

| # | 不确定点 | 本后端的口径 |
|---|---|---|
| 1 | 登录凭证字段名 | 固定为 `data.token`。前端 `user-normalizers.ts` 的候选数组只需保留第一项 |
| 2 | 用户 ID 字段名不统一 | `GET /auth/profile` 按示例用 `id`；`GET /admin/users` 按数据模型用 `user_id`。两种前端都认 |
| 3 | 物品状态字段名 | 列表与详情输出 `item_status`；管理端查询参数用 `status`。查询侧两者都接受 |
| 4 | 驳回理由的传递方式 | 审核请求体接受 `{"reject_reason": "..."}`，响应回传落库后的值。通过时不带请求体也能正常处理（空体不判参数错误） |
| 5 | 公告上下线没有独立接口 | 由 `PUT /admin/announcements/{id}` 承载：体里带 `announcement_status` 即生效 |
| 6 | 管理端接口列的请求体 | 那是鉴权中间件的上下文对象，后端不读取，只认 `Authorization` 头 |
| 7 | 列表不给总数 | 保持不给。前端按「本页条数是否装满 `page_size`」推断末页，后端不额外加字段 |

**一处例外说明**：#4 与 #5 是「接受」而非「必须」。审核时不带请求体、修改公告时只传部分
字段都能正常工作 —— 请求体解析对空体与缺字段都宽容，由 service 判断真正的必填项。
这样前端即使某天调整了提交内容，接口也不会因此报错。

## 7. 数据库与配置

默认 SQLite（纯 Go 驱动，不依赖 CGO）：`go run` 即可跑起来，评分环境无需额外装库。
切 MySQL 只改 `DB_DRIVER` / `DB_DSN` 两个环境变量，业务代码完全无感 ——
方言差异被隔离在 `internal/database`。

建表用 `AutoMigrate`：实体少而字段改动频繁，它保证表结构与 model 定义始终一致，
省去「改了结构体忘了改迁移脚本」这类只在特定环境才暴露的偏差。局限与破坏性变更的
处理流程见 [`../migrations/README.md`](../migrations/README.md)。

配置优先级为 `config/config.yaml` 默认值 → 环境变量覆盖，部署时改端口或密钥不必动文件。
`JWT_SECRET` 生产环境必须通过环境变量覆盖。
